## 一、这个项目是为了什么

### 1.1 一句话定位

**私有化本地知识库智能助手**：把你的文档放进自己电脑，用它提问，它基于你的文档
回答问题并标注引用出处——**全程不联网，数据不出本机**。

### 1.2 为什么做这个（背景）

这是本科毕业设计，采用**产品型**提交形式（学院允许"软件作品 + 设计说明书"，
此前置风险已于 2026-10-02 确认解除）。与"写论文做研究"的毕设不同，产品型毕设
要求交付一个**能运行、能演示、能验收**的完整软件。

选题时经过了多轮筛选，淘汰逻辑如下：

| 曾考虑的方向 | 淘汰/保留原因 |
|---|---|
| 工业设备数据方向（3 个候选） | 淘汰：依赖工业现场数据，**数据获取成本太高** |
| 公开 benchmark 研究型题目 | 可行，但最终决定把研究线拆出去，另写论文投稿 |
| **产品：本地知识库助手** | **选定**：数据自己造、指标可评估、系统可演示、风险可控 |

### 1.3 产品的四个核心卖点

这四个卖点同时是开题报告里需求规格的骨架：

1. **全程离线**——模型推理、向量检索都在本机完成，断网可完整工作；
2. **数据不出本机**——没有云 API 调用，隐私文档不外泄；
3. **答案可溯源**——每句回答标注 `[1] [2]` 引用编号，对应检索到的具体文档片段，
   杜绝"一本正经胡说八道"；
4. **档位可切换**——生成模型有轻量/默认/高配多档（不同参数量的 Qwen3 + 不同
   量化等级），现场演示时可以切换对比速度与质量。

## 二、最终形态与技术栈

### 2.1 最终产品长什么样

桌面端应用（Tauri 壳）：
- 左侧：提问区，流式输出答案；
- 右侧：检索轨迹可视化（这个问题检索了几路、命中哪些片段、各耗时多少）；
- 底部：实时读数条（内存/显存占用、每步耗时）。

**注意：这是最终形态。当前（2026-10-03）处于开发第 1 步刚完成的状态，
界面一行代码还没写**——这是刻意的：先把命令行链路跑通，再包服务，最后套壳。

### 2.2 分层架构与选型

| 层 | 技术 | 作用 | 为什么选它（对比过谁） |
|---|---|---|---|
| 桌面壳 | **Tauri v2**（未开始） | 打包桌面应用 | 要展示"峰值内存"指标，Electron 空应用就 ~370MB、内存高 50-75%，会灌水指标；Tauri ≈3MB |
| 前端 | **Vue3 + Vite**（未开始） | 界面 | 已有技术积累 |
| 后端服务 | **Python + FastAPI**（第 2 步） | 暴露 health/ingest/query/settings 接口 | 解析/检索/推理生态全在 Python；只绑 127.0.0.1，不对外 |
| 向量库 | **LanceDB** | 存片段+向量，混合检索 | 嵌入式（无需装数据库服务）；原生带向量检索 + BM25 全文检索 |
| 嵌入模型 | **BGE-M3**（MIT，0.6B） | 把文本变成 1024 维向量 | 中文 RAG 事实标准；一个模型同时产稠密+稀疏+多向量 |
| 生成模型 | **Qwen3-4B**（Apache-2.0） | 阅读检索片段、写带引用的回答 | 端侧可跑；同家族 4B/8B/14B 天然构成档位 |
| 推理引擎 | **llama.cpp（llama-server）** | 在 GPU 上跑 GGUF 模型 | 端侧事实标准；官方预编译 CUDA 包免编译 |
| 量化格式 | **GGUF Q5_K_M** | 把模型压到可进 6GB 显存 | Q5_K_M 约 2.9GB，质量保留 ~98% |

### 2.3 本机硬件与档位决策（重要）

实际开发机：**RTX 4050 Laptop（6GB 显存）+ 16GB 内存 + Windows 11 24H2**。

显存 6GB 意味着不能瞎选模型。权重必须"放得下 + 留出 KV cache 余量"：

| 档位 | 模型 | 体积 | 放置方式 | 用途 |
|---|---|---|---|---|
| light | Qwen3-4B Q4 | ~2.5GB | 纯 CPU | 兜底 |
| **default** | **Qwen3-4B Q5_K_M** | **~2.9GB** | **全显存** | 本机默认 |
| high | Qwen3-8B Q4_K_M | ~5GB | 2/3 层进 GPU，其余 CPU | 对比实验 |
| cloud | Qwen3-14B | ~9GB | 云 GPU 租用 | 评测基线 |

> 8B Q4 权重 ~5GB，6GB 卡扣掉系统占用后放不下权重+KV cache，所以默认档选
> 4B——这个"档位可现场切换"的设计本身就是产品卖点，而不是妥协。

## 三、给新手的五个核心概念

**RAG（检索增强生成）**：大模型直接回答会编造。RAG 的思路是"开卷考试"——
先从你的文档里检索相关片段，把片段塞给模型，要求它只根据片段回答。

**嵌入（Embedding）**：把一段文字变成一串数字（1024 个浮点数）。语义相近的
文字，向量距离就近。"电脑"和"计算机"的向量很近，所以向量检索能理解同义改写。

**BM25 与关键词检索**：按词频匹配的老式检索。对型号、编号这类精确词极其敏感，
但"电脑"搜不到只写"计算机"的文档。**向量检索和关键词检索的失败模式正好互补。**

**混合检索 + RRF**：两路各查一遍，用 RRF（Reciprocal Rank Fusion）融合——
每个文档的得分 = 它在各路结果里排名倒数的和（`score = Σ 1/(k+rank)`，k 通常
取 60）。不需要调分数归一化，工程上最省心。

**量化与 GGUF**：模型权重默认 FP16（每参数 2 字节）。量化压到 4~5 bit，
Q5_K_M 约保留 97~98% 质量、体积只剩 ~30%。GGUF 是 llama.cpp 的模型格式，
一个文件即装即用。

## 四、目前实现了什么（第 1 步：命令行链路）

### 4.1 目标与达成状态

第 1 步目标：**不碰任何界面，纯 Python 命令行跑通「导入 → 切分 → 嵌入 → 检索 →
生成」**。当前状态：**已完成并通过断网验证**。

### 4.2 代码结构（app/backend/，约 700 行）

```
localkb/
  config.py      全局配置：路径、四个模型档位、切分/检索/生成参数、离线开关
  chunker.py     导入 txt/md → 结构感知切分（md 标题节独立成块、段落合并、
                 长节滑窗 500 字/重叠 80 字）
  embedder.py    BGE-M3 封装：文本 → 1024 维向量（CUDA fp16，懒加载）
  store.py       LanceDB：建表/写入/向量检索/BM25 全文检索
  retrieve.py    检索编排：dense + BM25 双路召回 → RRF 融合 → 带 [编号] 引用
  llm_server.py  llama-server 子进程管理（启动/健康检查/停止，仅绑 127.0.0.1:8355）
  generator.py   调 llama-server 的 OpenAI 兼容流式接口生成回答
  cli.py         命令行入口：ingest / ask / stats 三个子命令
tests/test_chunker.py   切分单测（不依赖重型库）
```

### 4.3 实测验证结果（全部真实输出）

| 验证项 | 结果 |
|---|---|
| 切分单测 | 5/5 PASS |
| ingest 导入 | BGE-M3 上 GPU 加载 391 个权重张量，2 篇测试文档写入索引，27.8s |
| stats 统计 | 索引 2 块 / 2 来源，正确 |
| ask 联网 | 检索 dense 2 路 + FTS 2 路融合，回答分点、带 [1] 引用、RRF 公式正确 |
| **ask 断网** | **关闭 Wi-Fi 后完整跑通，回答质量不降——离线闭环证据达成** |

一次真实的断网问答（问题："什么是混合检索"）：

```
--- 检索（dense 2 路 + FTS 2 路，融合 2 条）---
  [1] 混合检索基础.md (rrf=0.0328)
  [2] 端侧量化基础.md (rrf=0.0323)
--- 回答（流式）---
混合检索（Hybrid Search）是指同时使用向量检索与关键词检索两路召回……
1. 向量检索：……擅长理解同义改写，但对精确词项不敏感 [1]。
2. 关键词检索：基于BM25……对精确词项极其敏感……[1]。
3. 融合方法：常用 Reciprocal Rank Fusion（RRF）……[1]。
```

### 4.4 一个体现严谨性的排障案例

断网首跑检索耗时 107s，联网对照 28s。排查过程：

1. 假设一"transformers 断网连 HuggingFace 超时"→ 加离线开关后联网仍 113s，
   **假设证伪**（开关保留，作为离线正确性保障）；
2. 对检索分段计时：各步骤合计仅 ~38s，与 113s 对不上；
3. 查进程：发现早前一次 ask 拉起的 **llama-server 残留进程占 2.94GB 内存**——
   Windows 下子进程不随父进程退出；
4. 结束残留进程后复跑：**38.4s**，根因坐实；
5. 修复：CLI 的 ask 命令增加退出时显式停止 llama-server，复跑确认无残留。

> 这个案例说明两件事：耗时问题要用**分段计时**定位而不是猜；每个假设都要被
> 证据证实或证伪，而不是停在"大概是这样"。

## 五、准备了什么

### 5.1 模型资产（E:\LocalKB\models\，共约 5.5GB，已全部就位）

| 文件 | 大小 | 来源 | 用途 |
|---|---|---|---|
| embedding/bge-m3/（11 个文件） | 2.27GB | 魔搭 ModelScope `BAAI/bge-m3` | 嵌入 |
| qwen3/qwen3-4b-q5_k_m.gguf | 2.89GB | 魔搭 `Qwen/Qwen3-4B-GGUF` | 生成 |
| llama-server/（llama.cpp b11335 CUDA 版） | 251MB + 373MB | GitHub Releases | GPU 推理服务 |

所有文件均与官方清单**逐字节核对大小一致**。

### 5.2 Python 环境（.venv）

torch 2.6.0+cu124（CUDA 可用）、lancedb 0.39、tantivy 0.26、pyarrow 25、
pandas 3.0、FlagEmbedding（含 transformers 5.18）、numpy 2.5、pytest 9.1。

### 5.3 测试语料（data/corpus/）

两篇自拟文档《混合检索基础》《端侧量化基础》，内容即本项目用到的技术原理，
方便自验证回答正确性。

### 5.4 下载渠道的实测结论（踩坑换来的，别再试错）

本机网络环境下各通道实测：

- **可用且快**：魔搭 ModelScope 直连（4~6MB/s，模型唯一可靠通道）；
  清华/阿里/腾讯 PyPI 镜像（Python 包）
- **不可用**：hf-mirror（代理 502/直连超时）、GitHub 资产直连、多个高校镜像
- **慢但可用**：ghproxy.net（50~380KB/s，支持分段并发续传）
- 教训：**从镜像代理下载的 zip 必须做 CRC 校验**——实测发生过分段拼接串包
  导致 zip 内部文件名与数据错位，靠"逐文件 CRC 校验 + 坏区间精确重下"定位。

## 六、怎么把它跑起来（三步）

```powershell
# 0. 前置：models/ 下模型已就位（见第五节），首次已配置好
cd E:\LocalKB\app\backend

# 1. 导入文档（把 txt/md 放进 data\corpus\ 后）
.venv\Scripts\python -m localkb.cli ingest E:\LocalKB\data\corpus

# 2. 查看索引
.venv\Scripts\python -m localkb.cli stats

# 3. 提问（首次会自动拉起 llama-server，回答流式输出并带引用编号）
.venv\Scripts\python -m localkb.cli ask "什么是混合检索"

# 换档位（4B/8B/CPU 三档）
.venv\Scripts\python -m localkb.cli ask "..." --profile high
```

验收判定：ingest 无报错且 stats 块数正确；ask 先打印双路召回与引用列表、再
流式输出带 `[编号]` 的回答；**断网后复跑 ask 仍完整出答案**（离线闭环）。

### 已知的待优化项（均已在开发记录中登记）

- CLI 每次冷启动要加载 BGE-M3（~33s）→ 第 2 步服务常驻后自然消失；
- 中文全文检索目前用单字切分兜底，召回粒度偏碎 → 计划换 jieba 预分词；
- 仅支持 txt/md，pdf/docx 解析在第 2 步补；
- BGE-M3 的稀疏向量（lexical weights）能力已留接口，当前用"稠密+BM25+RRF"
  组合，稀疏融合是后续增强项。

### 风险与对策

- **6GB 显存上限**：默认档 4B 全显存有余量；8B 需混合卸载，速度待实测（未验证）；
- **云 GPU 需求**：功能开发全程本机不租云；评测阶段（跑批量 benchmark、14B
  基线）按小时租 24GB 卡，预计几十元量级；
- **开题时间线**：距开题约 2 个月，先做系统的策略是为了让开题报告里的演示方案
  章节有真实可运行的系统背书。
